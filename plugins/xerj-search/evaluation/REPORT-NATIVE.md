这次已用原生 code search、definition、map 和批量搜索替换旧版自写的 `_search multi_match` 查询。对同一批题目，文件命中从旧适配器的 56.25% 提高到 68.75%，但仍低于本轮 Grep 基线的 93.75%；预设证据命中没有提高。四道真实模型题的总 Token 比本轮基线少 3.65%，八次任务中仍有五次耗尽预算。现有证据支持保留为按需启用的补充工具，尚不足以支持默认启用或替代 Grep。

## 实现与使用边界

| 插件工具 | 实际调用 |
| --- | --- |
| `XerjSearch` | 简单符号名调用 `xerj_def`，描述性问题调用 `xerj_code_search` |
| `XerjDefinition` | 显式调用 `xerj_def`，接受符号或能力描述 |
| `XerjMap` | 调用 `xerj_map`，查看指定项目前缀的索引结构与覆盖 |
| `XerjBatchSearch` | 调用 `xerj_batch_search`，保留各输入位置的命中、无结果和错误 |

入口是宿主的当前目录及插件数据目录。插件读取操作者配置，精确核对项目实际路径，再启动短期 `xerj mcp --disable-feedback` 进程；初始化后仅调用上表四种白名单工具。原生排序、定义选择、匹配窗口及弱匹配判断由 XERJ 完成。插件核对结果文件和片段属于当前项目，再把有限结果返回宿主；调用结束、超时或取消后回收子进程。不向模型转发上游初始化指令和整套工具清单。

配置缺失或 `enabled:false` 时回退；宿主插件禁用或会话未选择时工具不可见。模型无法覆盖可执行文件、地址、索引前缀、corpus 或根目录。仅连接 HTTP `127.0.0.1`，code search 的 corpus ledger 必须与配置 URL 和前缀相符。原生失败、弱匹配或没有可用证据时提供 Grep 参数；批量按原输入位置逐项回退。主动取消直接中止。

同一文件的不同定义和窗口会保留。重复文本优先用原生行号消歧；批量输出因上游预算只剩文件位置时保留已核验的文件，行号未知写为 `null`，不猜行号。普通返回上限 8 KiB，批量 16 KiB，原生 stdout 上限 1 MiB。批量优先减少正文，保留各问题的定位；模型继续用 Grep/Read 核实。

没有注册 autoindex、memory、反馈、Corpus Hub 管理或其他写工具。它们是 XERJ 另外的能力，不在本次代码与资料检索接入范围。PDF/Office、神经网络语义检索和跨语言向量模型没有参加此次测量。

## 固定检索：每题三次

两组各 48 个样本。每题最多两次检索操作、总检索预算 5 秒、保留输出 32 KiB；插件自身另外限制 8 KiB。正常插件调用使用 `timeoutMs:1500`，`limit:5`。两组均读取前五个不同文件，在命中行前后各取 12 行，每文件最多 4 KiB。

| 指标 | rg + 读取 | 原生插件 + 读取 |
| --- | ---: | ---: |
| 前五文件含人工答案 | 93.75% | 68.75% |
| 实际读到预设证据行 | 62.50% | 31.25% |
| 检索耗时中位数 | 2,203.0 ms | 243.2 ms |
| 检索耗时 P95 | 4,860.8 ms | 639.8 ms |
| 平均检索回包 / 后续读取 | 10,341 / 5,244 字节 | 3,822 / 4,031 字节 |
| 超时 / 错误 / 回退 | 2 / 0 / 0 | 0 / 0 / 0 |

| 类别 | rg 文件 / 证据命中 | 原生插件文件 / 证据命中 |
| --- | ---: | ---: |
| 确切符号 | 75% / 75% | 100% / 100% |
| 英文功能描述 | 100% / 50% | 75% / 0% |
| 中文需求 | 100% / 75% | 25% / 0% |
| 文档定位 | 100% / 50% | 75% / 25% |

原生调用全部真实命中 XERJ。42/48 次存在候选或返回裁剪；21 个样本中的 60 个命中片段触发单片段长度限制。基线有三次输出裁剪。文件命中提高没有带来预设证据行命中提高：返回相关文件后，仍需要进一步选词与读取。预设证据只是人工提前选定的可核查位置，不是所有合理答案的穷尽集合。

相对 0.1 适配器，原生符号命中保持 100%，中文文件命中 0% → 25%，文档文件命中 50% → 75%；总体 56.25% → 68.75%，证据仍为 31.25%。旧适配器耗时不可与新版直接归因为实现差异：本轮还修正了基线协议。

原脚本额外使用 `rg --sort path`，在本机导致串行扫描及大量超时，初次重测 44/48 个基线样本超时，降级演练也失败；保留为 [无效重测](results/retrieval-native.json)。检查宿主 Grep 后移除该额外排序，并加 `--no-config` 排除外部配置，收集完后仍按原有规则排序。有效重测使用 `rg-parallel-no-config-v2`，题目、模式及预算均未变。不能把基线耗时变化算成插件收益。

基线关键词由人工预先提供，不能代表模型自主构造查询；全语料扫描也不能代表人工先缩小目录的效果。重复查询受到文件与索引缓存影响，不推算通用速度倍率。两组字节格式和返回内容不同，字节变化不换算为 Token 节省。[有效原始检索结果](results/retrieval-native-parallel.json) · [阅读摘要](results/retrieval-native-parallel.md) · [协议与评分](README.md)

## 真实模型 A/B

沿用首轮选法：每类第一题，四题各两组。使用现有 `deepseek / deepseek-flash` 配置及真实 Vykor QueryEngine、插件独立进程、Grep/Read。system/user prompt 与原实验一致，有 XERJ 时先尝试、证据不足继续 Grep。每次运行独立上下文，最多六次模型 HTTP，每请求输出上限 1,024 Token，无自动重试。

旧 0.1 实验的 14.59% 和初次无效原生实验的汇总均不作为本轮收益。主要记录：[更正后的原始 A/B](results/agent-ab-native-corrected.json) · [固定提示与权限配置](results/agent-ab-native-corrected.selection.json)

## Map 与批量控制查询

另用完全相同的 16 题按原顺序分成四组，每组四题；显式 Map 一次，Batch 四次，每题最多五条，原生共享 `max_tokens:2000`、插件输出 16 KiB。没有模型请求，不测模型 Token。上游该预算是词边界估算，不能等同供应商 Token。

| 项目 | 实测 |
| --- | ---: |
| Map 返回的项目索引 / 耗时 | 3 / 154.3 ms |
| 批量调用 / 所含问题 | 4 / 16 |
| 四次批量检索合计耗时 | 880.7 ms |
| 文件命中 / 证据命中 | 11/16 / 5/16 |
| 逐项错误 | 0 |
| 只剩定位的命中 / 其中行号未知 | 75 / 39 |

此控制查询单独使用 5 秒配置。原 1.5 秒批量试验有两批整体超时、8/16 项错误；保留 [原始结果](results/batch-native.json)。延长到 5 秒后又发现上游预算会移除原始 `_source`，只在 `citation` 留下文件位置。插件改为恢复这些原生引用，并允许明确无行号的文件定位；不伪造正文或行号。预算处理先保留定位再删正文，已有对应回归测试。各中间结果及一次复现脚本上下文错误也保留，详见 [结果清单](results/README.md)。

最终 [批量结果](results/batch-native-verified.json) `valid:true`。Map 没有单独验证答案召回；其价值是查看索引结构和覆盖。批量减少宿主工具调用次数的机制已经验证，但这是一次热缓存控制查询，不能拿 880.7 ms 与三次重复单题测试推算稳定加速倍数或模型收益。生产默认超时仍是 1.5 秒，批量较多时操作者可调整 `timeoutMs`；本文没有静默放宽主实验预算。

复现批量控制查询：

```powershell
node evaluation/batch.mjs --root C:/path/to/frozen-corpus --config-dir C:/path/to/5s-plugin-data --output evaluation/results/new-batch.json
```

输出必须使用新文件名；语料锚点在前后校验，错误、回退和未知行号均明确记录。
