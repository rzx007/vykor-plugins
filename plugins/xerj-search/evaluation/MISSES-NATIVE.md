# 原生检索漏检逐题分析

> 后续 [0.2.1 修复重测](REPORT-021.md) 已实现格式、定位和读取提示修复。本页保留诊断时的过程与限制，五道文件漏检仍存在。

日期：2026-10-27。分析对象：0.2.0 插件、XERJ v1.0.0-rc.99、原固定 16 题及冻结索引。生产插件没有修改，没有新模型 API 请求；所有探查均为本地检索及离线核对。

本轮使用 BM25，即按字词、频率和文本长度等因素排序；没有自动把中文需求对应到英文变量名的语义模型。下文的“词法限制”指这种按字词匹配的限制。

结论需要比前次报告更细分：五道题漏了目标文件，另外六道题找到了文件但未通过原“后续读取窗口”的证据评分。后者中四题的证据实际已经在插件回包里；调整读取位置还能恢复第五题。五道文件漏检都找到过可恢复目标的查询，但这是逐题调试后的控制试验，不能据此宣称新的 100% 命中率。

*“已有证据”只检查原报告实际保存的片段与读取内容。Grep 的原始 JSON 流没有完整保存，不能追溯其所有可能可见的命中，因此此行不作为新的公平 A/B 指标。原生四题的已返回证据则可逐行直接确认。[离线重读原始数据](results/diagnosis-native/window-policy.json)

## 确认存在的插件适配问题

捕获实际 `xerj_code_search` MCP 回包，再与解析候选、文件核验、最终输出逐层对比，确认以下问题：

1. **把格式说明当成源码。** 原生长函数结尾附有 `... [function … truncated at … chars]`；预算紧张时还附有定位占位、整页 passage 计数及预算说明。当前解析未完整移除这些文字，核验时在源码找不到，于是整段被拒绝。附件文档题的这一页，五条原生命中只留下了一条。
2. **混用了命中行和定义起点。** 原生标题位置与后续 `function … @ line N` 标签可以不同；当前只使用前者。对照中 `grep.ts` 的首段实际在 8–36 行，但某个查询的标题行是 37，于是唯一、正确的正文也被拒绝。应保留两个位置，按当前原文核验实际片段，重复文本仍须消歧。
3. **统一字节限额容易切掉中文段落末尾。** 1,500 字节不等于 1,500 字；工具状态保留题就是可复现例子。增大上游 `full` 不会自动解决下游裁剪，适合优先改善阅读位置与范围提示。
4. **`k=5` 是五条原生记录，不保证五个不同文件。** 原生允许同文件的多个片段，拒绝或去重后也不自动补足文件。可以适量多取候选后保留五个不同文件及其位置，但本轮五道文件漏检不能单靠这个改动恢复。

离线解析原型只剥离已确认的上游格式、采用定义标签定位，并保留原文和路径核验；不改变排序、问题、索引和输出限额。它让多道题从 1–3 条有效片段恢复到 4–5 条，**原五道文件漏检仍然漏检**，不能把它夸大成召回提升。正式修复需补真实回包格式的回归测试，本轮没有改生产代码。[原始边界](results/diagnosis-native/boundaries.json) · [有界适配对照](results/diagnosis-native/adapter-bounded.json)

## 索引配置与 XERJ 版本各承担什么

11 道证据未命中题涉及的 13 个目标锚点均在已索引正文内。每个目标都有文件记录，关键文字完整；因此没有发现漏扫描、文件类型未识别、正文缺失或未完成索引。索引无需为修复漏文件而重建。[索引与实际分词核对](results/diagnosis-native/index.json)

配置确有三项适用性限制：

- 已启用 `code` 分析器（把文本拆成搜索词的规则），实际能把 `validateJsonSchemaInput` 拆成 validate / json / schema / input；不能再把“打开 code 分词”作为未做的优化。
- 同一主要索引混合代码、中文说明和历史设计，默认 `code` 分词把中文问题拆成单字。这会让大量通用汉字重叠的设计文档参与竞争。XERJ 本身有 `cjk` 双字分词，本地 `_analyze` 已确认，但**没有重建临时索引验证其召回收益**，不能承诺切换必然改善；它也不解决中文到英文标识符的语义对应。
- 原索引显式使用 `--no-semantic`，没有 `semantic_text`。实测把模式改成 hybrid 只得到明确的 `BM25 only` 提示。要评估语义检索，需要真正的多语言神经模型和相应索引，不能只改模式或把词法向量当作语义能力。此项未测。

在这版 XERJ 原生实现中还确认：

- 定义选择和窗口选择提取的查询词限于 ASCII 标识符；纯中文问题在这一层提取不到词，窗口回到正文开头。覆盖加分按空格划分问题，完整中文句子也难以进入英文多词问题的覆盖处理。这是当前原生管线的语言限制，不是全文引擎没有中文支持。[rc.99 选段实现](https://github.com/xerj-org/xerj/blob/e3c14a28dfb9fd677f650e310630db51cea431b0/engine/crates/xerj-common/src/xccode/passage.rs#L14) · [覆盖排序实现](https://github.com/xerj-org/xerj/blob/e3c14a28dfb9fd677f650e310630db51cea431b0/engine/crates/xerj-common/src/code_query.rs#L221)
- 长定义在 rc.99 取头部，并会在嵌套定义前收紧范围。相关词在参数说明、签名或别的方法中时，文件命中不代表返回了目标实现。[rc.99 定义片段](https://github.com/xerj-org/xerj/blob/e3c14a28dfb9fd677f650e310630db51cea431b0/engine/crates/xerj-common/src/xccode/passage.rs#L110)
- 本地另一个固定上游提交 `d435fb9` 已有 #2464 的长定义窗口修正，说明这项限制具有版本差异；没有运行该版本二进制，不能将源码变化等同已测收益，也不能声称所有问题在新版已解决。[固定提交中的实现](https://github.com/xerj-org/xerj/blob/d435fb9c780c26d312e7cddae2b7ac5ec0f28f07/engine/crates/xerj-common/src/xccode/passage.rs#L160)

## Grep 对比还包含人工提示优势

基线用的不是原自然语言问题，而是事先由人工写好的正则。例如图片题直接获得 `nativeImageAvailable`，保护题获得 `validateJsonSchemaInput/maxConcurrentCalls`，数据目录题获得 `dataDir/getPluginDataDir`，计划题获得 `ScheduleRepository/createRun`。原生组只得到原问题。

把这五道文件漏检的既定基线模式转换成关键词、交给相同原生管线后，五题都能找到目标文件。这个正向控制只能说明词法索引可按已知标识符找到代码，不能作为插件的新成绩；这些关键词来自人工答案附近，不应放进实际测试或生产查询。[人工关键词正向控制](results/diagnosis-native/oracle-keywords.json)

所以原 93.75% 对 68.75% 反映了“人工帮助的 Grep 流程”和“直接自然语言原生流程”的差异，也混入了适配问题；它不能单独证明搜索引擎本身能力的差距。保留这组实际工作流测量，同时应另用未参与调试的新题，公平比较 Agent 自主选词、改写、缩小范围及回退。

## 改进顺序

1. **先修适配和读取策略。** 清理格式文字、保留命中行与定义起点、处理未知行号；让 Read 理解已返回片段范围。离线已有 31.25% → 62.5% 的证据支持，不需要重新索引。
2. **再改善查询选择。** 中文代码问题增加一个英文技术表达，英文文档问题允许检索资料语言；按问题使用安全的语言或资料范围过滤，保留 Grep 回退。不要自动丢弃所有测试或历史文档，也不要把事后手调写成固定答案规则。
3. **最后测试版本和索引改造。** 在同一题集上做版本对照，再用独立新题检查；CJK 双字字段、多语言语义检索各开临时索引分别测。当前没有证据支持直接承担神经模型初始化与索引成本。

这轮确认了可提升空间，也确认仅修解析不能解决五道文件漏检。旧 Token 降幅 3.65% 及模型完成情况没有改变；新读取策略、查询改写的模型收益仍须另测。
